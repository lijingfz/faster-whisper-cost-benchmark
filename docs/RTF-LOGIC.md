## 1. Definition of RTF

This project uses the **throughput-oriented** definition of RTF (higher is better):

```
RTF = audio duration (s) ÷ transcription wall-clock time (s)
```

See `src/bench_core.py`:

```python
res.rtf = audio_duration_s / res.median_time_s
```

It means "how many hours of audio can be transcribed per wall-clock hour". For example, if
600 seconds of audio is transcribed in 12 seconds, RTF = 50x.

> Note: some literature defines RTF as processing time ÷ audio duration (lower is better),
> which is the reciprocal of this project's definition. To avoid ambiguity, this project's
> reports always label it "RTF（倍速）" (RTF as a speed multiple).

<details>
<summary>中文：一、RTF 的定义</summary>

本项目采用**吞吐方向**的 RTF 定义（越大越好）：

```
RTF = 音频时长（秒） ÷ 转写墙钟耗时（秒）
```

实现见 `src/bench_core.py` 中：

```python
res.rtf = audio_duration_s / res.median_time_s
```

含义是「每 1 个墙钟小时能转写多少音频小时」。例如 600 秒的音频 12 秒转完，
RTF = 50x。

> 注意：部分文献将 RTF 定义为 处理时间 ÷ 音频时长（越小越好），与本项目的定义
> 互为倒数。本项目报告中统一写作「RTF（倍速）」以避免歧义。

## 2. Numerator: Audio Duration

`ffprobe_duration()` in `benchmark.py` calls ffprobe to read the duration of the audio
container, giving `audio_duration_s`. It is a fixed constant within one sweep round; but in
the adaptive flow, if "segment starvation" occurs (see Section 5), the audio is
re-concatenated to be longer and `audio_duration_s` is updated accordingly.

**Why the audio must be long enough** (see `prepare_audio.py`):
`BatchedInferencePipeline` first uses VAD to split long audio into speech segments, then feeds
them to the GPU for decoding in parallel batches of batch_size. `large-v3` works in 30s
windows; **if the audio is too short, it yields fewer segments than batch_size**, so large
batches "can't be filled" — not only does this fail to measure the real throughput, but VRAM
also plateaus long before the hardware limit (**segment starvation**). RTF is a ratio and
does not depend on the absolute audio length: as long as every instance in a comparison uses
the same audio (or audio generated by an equivalent rule), the comparison is fair.

> Measured example: with the 275.5s base audio concatenated to only 3× (826s), G7's VRAM got
> stuck at 13/31 GiB and its RTF stuck at ~132x from batch_size ≥ 32 onward — a **false
> plateau** caused by segment starvation, which underestimates strong GPUs. Only by switching
> to a 32× start, lengthening the audio adaptively when needed, could VRAM be pushed to its
> real limit. (The current default starts at 20×.)

<details>
<summary>中文：二、分子：音频时长</summary>

`benchmark.py` 中的 `ffprobe_duration()` 调用 ffprobe 读取音频容器的 duration，
得到 `audio_duration_s`。在一轮扫描内它是固定常数；但在自适应流程里，若发生「段饥饿」
（见第五节），音频会被重新拼长，`audio_duration_s` 随之更新。

**为什么音频要足够长**（见 `prepare_audio.py`）：
`BatchedInferencePipeline` 先用 VAD 把长音频切成语音段，再按 batch_size 并行送入
GPU 解码。`large-v3` 按 30s 窗口工作，**音频太短则切出的段数少于 batch_size**，大
batch「填不满」——不仅测不出真实吞吐，显存也会在远未到硬件极限时就走平（**段饥饿**，

份（或等价生成规则的）音频即可公平比较。

> 13/31GiB、RTF 卡在 ~132x 不动——这是段饥饿造成的**假平台**，会低估强卡。改用
> 32× 起步、并在需要时自适应加长，才能把显存推到真实极限。（当前默认 20× 起步）

## 3. Denominator: Measuring Wall-Clock Time

A single timing is done in `transcribe_once()` (`src/bench_core.py`), with three key details:

```python
torch.cuda.synchronize()          # ① sync before the start to flush pending GPU work
t0 = time.perf_counter()
segments, _info = pipeline.transcribe(audio_path, batch_size=batch_size, language=language)
text_parts = [seg.text for seg in segments]   # ② iterate the generator to trigger computation
torch.cuda.synchronize()          # ③ sync again before the end so the GPU has really finished
elapsed = time.perf_counter() - t0
```

1. **Two `cuda.synchronize()` calls**: CUDA calls are asynchronous. Without syncing, the
   timer only measures the time to *launch* the work, not the time for it to *complete*.
2. **Fully consume the segments generator**: faster-whisper's `transcribe()` is lazy and
   does almost no computation before returning; without iterating the segments, the measured
   time would be falsely close to 0. This is the most common pitfall when benchmarking this
   library.
3. **The timing window covers the whole pipeline**: audio decoding, VAD segmentation, feature
   extraction, and GPU decoding are all included. So this is end-to-end throughput, not pure
   GPU kernel time.

<details>
<summary>中文：三、分母：墙钟耗时的测量</summary>

单次计时在 `transcribe_once()`（`src/bench_core.py`），有三个关键细节：

```python
torch.cuda.synchronize()          # ① 起点前同步，清掉未完成的 GPU 队列
t0 = time.perf_counter()

```

1. **两次 `cuda.synchronize()`**：CUDA 调用是异步的。不同步的话，计时器量到的
   只是「发起任务」的时间，而非「计算完成」的时间。
2. **完整消费 segments 生成器**：faster-whisper 的 `transcribe()` 是惰性的，返回
   时几乎没做计算；不迭代 segments，耗时会假到接近 0。这是该库基准测试最常见
   的坑。
3. **计时窗口覆盖全流程**：音频解码、VAD 切段、特征提取、GPU 解码全部计入。
   因此这是端到端吞吐，不是纯 GPU kernel 时间。

</details>

## 4. Noise Reduction

Single timings fluctuate, so the project applies three layers of control:

| Measure | Location | Purpose |
|---|---|---|
| Warm-up run (excluded from results) | `benchmark.py` | Excludes one-off costs such as CUDA context initialization, kernel compilation, and VRAM allocation |
| Run each batch size `--runs` times and take the **median** (default: 1 run) | `sweep_batch_sizes()` | The median is more robust to occasional jitter than the mean |
| Fixed language `--language en` | `benchmark.py` | Skips per-run automatic language detection, eliminating that source of timing variance |

During measurement, a `GpuMemSampler` background thread also samples **device-level** VRAM
every 50 ms via `torch.cuda.mem_get_info()` and records the peak — this captures VRAM that
CTranslate2 allocates outside torch's caching allocator. It runs in a separate Python thread,
so its interference with GPU timing is negligible.

<details>
<summary>中文：四、降噪处理</summary>

单次计时有波动，项目做了三层控制：

| 手段 | 位置 | 作用 |
|---|---|---|
| 预热运行（不计入结果） | `benchmark.py` | 排除 CUDA context 初始化、kernel 编译、显存分配等一次性开销 |
| 每档跑 `--runs` 次取**中位数**（默认 1 次） | `sweep_batch_sizes()` | 中位数对偶发抖动比平均数更稳健 |
| 固定语种 `--language en` | `benchmark.py` | 跳过每次运行的语种自动检测，消除该部分耗时波动 |

测量期间另有 `GpuMemSampler` 后台线程以 50ms 间隔用 `torch.cuda.mem_get_info()`
做**设备级**显存采样，记录峰值——可捕获 CTranslate2 在 torch 缓存分配器之外分配的
显存。它运行在独立 Python 线程，对 GPU 计时的干扰可忽略。

</details>

## 5. Adaptive VRAM Saturation: Pushing the GPU to Its Limit

The goal of this project is not to "stop early once the RTF knee is found", but to **push VRAM
to its physical limit (filling ~90% or blowing it up with an OOM) and measure RTF / time /
cost in that state**. To do this, it automatically probes upward along two dimensions:

1. **Batch dimension** (`sweep_batch_sizes(..., saturate=True)`): keeps increasing the batch
   until VRAM is full / blown.
2. **Audio dimension** (the adaptive loop in `benchmark.py`): when a larger batch can no
   longer push VRAM higher yet VRAM is still not full (segment starvation), it automatically
   lengthens the audio and runs another round.

<details>
<summary>中文：五、自适应显存占满：把 GPU 推到极限</summary>

本项目的目标不是「浅尝辄止找 RTF 拐点」，而是**把显存推到物理极限（占满 ~90% 或
OOM 打爆），并在该状态下测 RTF / 耗时 / 成本**。为此有两个维度的自动上探：

1. **batch 维度**（`sweep_batch_sizes(..., saturate=True)`）：一路增大 batch 直到显存打满/打爆。
2. **音频维度**（`benchmark.py` 的自适应闭环）：当 batch 已无法再推高显存却仍未占满
   （段饥饿）时，自动加长音频再来一轮。

</details>

### 5.1 Upward Probing Along the Batch Dimension (saturate mode)

The physical mechanism behind how VRAM and RTF change with batch_size: each time, the pipeline
takes batch_size VAD speech segments and feeds them to the GPU for parallel decoding. The
larger the batch, the more fully the parallel units are filled, the higher the VRAM usage, and
the higher the RTF — until VRAM nears its limit (the OOM boundary) or the speech segments run
out.

When `saturate=True`, `sweep_batch_sizes`:

- **Disables the RTF-saturation early stop** (it doesn't give up just because RTF flattens;
  the goal is to push VRAM).
- First tests each candidate given by `--batch-sizes` (default `1,4,8,16,32,48,64,80,96`) in
  turn.
- After reaching the end of the candidates, it **dynamically appends larger batches**: if VRAM
  at the largest size is still rising relative to the previous size (> `vram_plateau_epsilon`,
  default 3%), it appends `batch×2` and continues, until
  - a **CUDA OOM** is raised → that size is marked `oom` and the sweep stops (VRAM is blown,
    i.e. the hardware limit is reached); or
  - VRAM **no longer rises with batch** (plateau) → upward probing stops (going bigger won't
    help); or
  - the `--max-batch` safety cap (default 1024) is reached.

<details>
<summary>中文：5.1 batch 一维上探（saturate 模式）</summary>

显存与 RTF 随 batch_size 变化的物理机制：pipeline 每次取 batch_size 个 VAD 语音段
并行送入 GPU 解码。batch 越大，并行单元填得越满、显存占用越高、RTF 上升；直到显存
接近上限（OOM 边界）或语音段被取空。

`sweep_batch_sizes` 在 `saturate=True` 时：

- **关闭 RTF 饱和提前停止**（不因 RTF 走平就收手，目标是推显存）。
- 先按 `--batch-sizes` 给定的候选（默认 `1,4,8,16,32,48,64,80,96`）逐档测。
- 扫到候选末尾后**动态追加更大 batch**：若最大档显存相对上一档仍上涨
  （> `vram_plateau_epsilon`，默认 3%），追加 `batch×2` 继续；直到
  - 抛出 **CUDA OOM** → 标记该档 `oom`，停止（显存已打爆，达到硬件极限）；或
  - 显存**不再随 batch 上涨**（平台）→ 停止上探（再大也没用）；或
  - 触及 `--max-batch`（默认 1024）安全上限。

</details>

### 5.2 VRAM Saturation Summary (`summarize_sweep()`)

After a sweep round finishes, `SweepSummary` summarizes it:

| Field | Meaning |
|---|---|
| `oom` | Whether an OOM was hit (VRAM blown) |
| `peak_vram_gib` | Max peak VRAM across all batch sizes in this round |
| `vram_utilization` | `peak_vram / total VRAM` |
| `saturated` | `oom` or `vram_utilization ≥ vram_target_frac` (default 0.90) |
| `vram_climbing` | VRAM is still rising across the last two ok sizes (can still be pushed higher via batch) |
| `starved` | **Not saturated and VRAM has plateaued** ⇒ too few speech segments; the audio must be lengthened |

<details>
<summary>中文：5.2 显存饱和汇总（<code>summarize_sweep()</code>）</summary>

一轮扫描结束后，用 `SweepSummary` 汇总：

| 字段 | 含义 |
|---|---|
| `oom` | 是否触发过 OOM（显存被打爆） |
| `peak_vram_gib` | 本轮所有档位的最大峰值显存 |
| `vram_utilization` | `peak_vram / 总显存` |
| `saturated` | `oom` 或 `vram_utilization ≥ vram_target_frac`（默认 0.90） |
| `vram_climbing` | 最后两个 ok 档显存仍在上涨（可继续靠 batch 推高） |
| `starved` | **未饱和 且 显存已平台** ⇒ 语音段不足，需要加长音频 |

</details>

### 5.3 Adaptive Audio Dimension (the `benchmark.py` loop)

```
multiplier = 20                       # starting audio = base × 20 (default)
loop (at most --max-iterations rounds):
    generate audio of base × multiplier
    results = sweep_batch_sizes(..., saturate=True)
    summary = summarize_sweep(results, total_vram, vram_target_frac=0.90)
    if summary.saturated:             # saturated (≥90%) or blown by OOM
        break                         # done
    if summary.starved:               # VRAM plateaued but not full => segment starvation
        multiplier *= audio_grow_factor   # audio ×2, re-sweep
    else:
        break                         # not starved (e.g. batch already probed to its cap), stop
    bounded by --max-audio-multiplier / --max-iterations
```

**Why segment starvation calls for longer audio rather than a larger batch**: if VRAM stops
rising as the batch grows, the available speech segments have run out and the batches can't
be filled, so adding more batch just spins idle. At that point the only way to raise GPU
utilization is to supply more speech segments, i.e. concatenate the audio to be longer.

<details>
<summary>中文：5.3 音频维度自适应（<code>benchmark.py</code> 闭环）</summary>

```
multiplier = 20                       # 起始音频 = base × 20（默认）
loop (最多 --max-iterations 轮):
    生成 base × multiplier 的音频
    results = sweep_batch_sizes(..., saturate=True)
    summary = summarize_sweep(results, 总显存, vram_target_frac=0.90)
    if summary.saturated:             # 已占满(≥90%)或 OOM 打爆
        break                         # 完成
    if summary.starved:               # 显存平台却没占满 => 段饥饿
        multiplier *= audio_grow_factor   # 音频 ×2，重扫
    else:

    受 --max-audio-multiplier / --max-iterations 限制
```

**为什么段饥饿要加长音频而不是继续加 batch**：显存在增大 batch 时不再上涨，说明
可用语音段已被取空、批次填不满，再加 batch 也是空转。此时唯一能提高 GPU 占用的
办法是提供更多语音段，即把音频拼得更长。

</details>

### 5.4 Selecting the Two Optimal Batch Sizes

The same sweep data yields two perspectives at once (`src/bench_core.py`):

```python
pick_optimal(results)      # cost-optimal ⭐: the ok size with the highest RTF (lowest $/audio-hour)
pick_saturating(results)   # VRAM-saturated 🔥: the ok size with the highest peak VRAM
```

- **Cost-optimal ⭐**: since `$/audio-hour = hourly price / RTF`, the highest RTF means the
  lowest unit cost.
- **VRAM-saturated 🔥**: reports RTF / time / cost for the size where the GPU is most fully
  loaded, answering "how fast and how cost-effective is it with the GPU fully used".

The report (`src/report.py`) gives RTF, median inference time, peak VRAM, and cost per audio
hour for both.

<details>
<summary>中文：5.4 两个最优档的选取</summary>

同一份扫描数据同时给出两个视角（`src/bench_core.py`）：

## 6. Converting RTF to Cost

In `src/report.py`:

```python
cost_per_audio_hour = price_per_hour / r.rtf
```

Derivation: RTF = audio hours transcribed per wall-clock hour ⇒ transcribing 1 hour of audio
takes `1/RTF` machine hours ⇒ multiplying by the instance's hourly price gives the cost per
audio hour. **At a fixed hourly price, the highest RTF gives the lowest unit cost** — which is
exactly the objective function of the cost-optimal size. The report gives the cost per audio
hour for both the cost-optimal size ⭐ and the VRAM-saturated size 🔥.

<details>
<summary>中文：六、RTF 与成本的换算</summary>

`src/report.py` 中：

```python
cost_per_audio_hour = price_per_hour / r.rtf
```

推导：RTF = 每墙钟小时可转写的音频小时数 ⇒ 转写 1 小时音频需要 `1/RTF` 个
机器小时 ⇒ 乘以实例时价即每音频小时成本。**时价固定时，RTF 最大即单位成本
最低**——这正是成本最优档的目标函数。报告同时给出成本最优档 ⭐ 与显存占满档 🔥
两者的每音频小时成本。

## 7. Trade-offs and Applicability

**Implicit assumptions**: VRAM increases monotonically with batch (up to OOM), and VRAM that no
longer rises with batch means the speech segments have run out (segment starvation). This
basically holds for batched decoding.

**Strengths**:
- Every machine is measured in a "VRAM fully loaded" state, so strong GPUs are not
  underestimated because of insufficient audio / batch;
- OOM and the VRAM plateau both serve as explicit stopping boundaries, so the whole process is
  automatic with no manual parameter tuning;
- Segment starvation automatically lengthens the audio, avoiding the rule-of-thumb problem of
  picking an audio length by gut feeling.

**Limitations and caveats**:
- The longer the audio and the more iterations, the longer each sweep takes. Starting at 32×
  (about 8800s) is usually enough to feed up to bs≈256; use `--audio-multiplier` / `--runs`
  to tune the runtime, and `--max-iterations` / `--max-audio-multiplier` as backstops against
  unbounded growth.
- The saturation threshold `--vram-target-frac` (default 0.90) is the line at which VRAM
  "counts as saturated"; it deliberately does not aim for exactly 100%, leaving headroom for
  fragmentation and avoiding needless repeated OOMs.
- This benchmark measures **single-process, single-audio-stream offline throughput** (the
  denominator is end-to-end wall-clock time, and each batch size is repeated serially). In
  production, if multiple processes feed multiple audio files concurrently, actual utilization
  and cost may be better; this benchmark gives a conservative lower bound.
- To fall back to the legacy "early stop on RTF saturation, don't chase full VRAM" behavior,
  add `--no-saturate`.

<details>
<summary>中文：七、方法的取舍与适用边界</summary>

**隐含假设**：显存随 batch 单调递增（到 OOM 为止）；显存不再随 batch 上涨即说明
语音段被取空（段饥饿）。在 batched 解码场景基本成立。

**优点**：
- 每台机器都测在「显存吃满」状态，强卡不会因音频/ batch 不足被低估；
- OOM 与显存平台都作为明确的停止边界，全程自动、无需人工试参数；
- 段饥饿自动加长音频，避免了「音频拍脑袋定长」的经验值问题。

**局限与注意**：
- 音频越长、迭代越多，单轮扫描越久。32× 起步（约 8800s）通常足以喂满到 bs≈256；
  可用 `--audio-multiplier` / `--runs` 调节耗时，用 `--max-iterations` /
  `--max-audio-multiplier` 兜底防止无限增大。
- 占满阈值 `--vram-target-frac`（默认 0.90）是「视为占满」的判定线，不追求恰好 100%
  以留出碎片余量、避免不必要的 OOM 反复。
- 本基准测的是**单进程、单音频流的离线吞吐**（分母为端到端墙钟时间、每档串行
  重复）。生产上若多进程并发喂多个音频，实际利用率与成本可能更优，本基准给出的
  是保守下界。
- 需要退回旧的「RTF 饱和提前停止、不追求占满」行为时，加 `--no-saturate`。

</details>
